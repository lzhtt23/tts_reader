## 一、这份文档要回答什么

用户问的是「legado 的书源导入原理，能不能加进桃花源阅读器」。

调研结论分两半，**必须分开看**，否则会得出错误的工作量估计：

| 问题 | 答案 |
| --- | --- |
| 能不能「导入 legado 书源」？ | **能**，半天到一天，不需要新依赖 |
| 导入后能不能「用它抓书朗读」？ | **能，但那不是导入的工作量**，是重写一套规则引擎 + 在线书籍链路 |

> ⚠️ **核心提醒**：桃花源现在的「书源」和 legado 的「书源」**不是同一个东西**，
> 名词一样、结构完全不兼容。直接说「加个导入」会严重低估工作量。
> 详见 §2。

## 二、先厘清：两边的「书源」根本不是一回事

### 2.1 桃花源现在存的是什么

`lib/models/web_link.dart` 的 `WebLink`：

```dart
class WebLink {
  final String title;
  final String url;        // 就是一个网址
  final DateTime createdAt;
  final bool isShortcut;
}
```

`lib/pages/book_sources_page.dart:167` 的页面说明写得很直白：

> 「这里只存网址，浏览器菜单「书源」里点一下就直接打开。」

**本质是书签列表。** 存的是 *去哪儿*（URL）。

### 2.2 legado 存的是什么

`data/entities/BookSource.kt` 是一个 Room 实体，字段有三十多个：

```
bookSourceUrl      ← 主键
bookSourceName / bookSourceGroup / bookSourceType
lastUpdateTime / respondTime / weight
searchUrl    + ruleSearch      ← 搜索：URL 模板 + 解析规则
exploreUrl   + ruleExplore     ← 发现
               ruleBookInfo    ← 详情解析
               ruleToc         ← 目录解析
               ruleContent     ← 正文解析
loginCheckJs / coverDecodeJs / eventListener / customButton / homepageModules
```

**存的是 *怎么挖*。** 不是网址，是爬虫规则。

### 2.3 结论

- `WebLink` 和 `BookSource` 唯一的重叠是「都有一个 URL 字段」
- 把 legado 书源转成 `WebLink`，只能得到「一堆网站首页」，**丢掉的正好是全部有用信息**
- 所以不存在「把 legado 源塞进现有书源列表就完事」这种便宜路子

## 三、legado 的导入原理（已逐行核实）

这一节是把 legado 的导入链路完整拆开，**已读源码确认**，可作为独立实现的依据。

### 3.1 入口：自定义 scheme

`AndroidManifest.xml` 给 `OnLineImportActivity` 注册了两个 scheme：

```xml

          android:exported="true"
          android:theme="@style/AppTheme.Transparent">
    <intent-filter>
        <action android:name="android.intent.action.VIEW" />
        <category android:name="android.intent.category.DEFAULT" />
        <category android:name="android.intent.category.BROWSABLE" />
        <data android:scheme="legado" />
        <data android:scheme="yuedu" />
    </intent-filter>
</activity>
```

`OnLineImportActivity.kt:15` 的类注释给出了格式：

```
legado://import/{path}?src={url}
```

### 3.2 分派：按 path 走不同导入器

`OnLineImportActivity.onCreate()`（L51–L99）先取 `src`，取不到直接 `finish()`，
然后按 `intent.data.path` 分派：

| path | 去向 |
| --- | --- |
| `/bookSource` | → `MainActivity.createBookSourceManageIntent(src)` |
| `/rssSource` `/replaceRule` `/textTocRule` `/httpTTS` `/dictRule` `/theme` | 各自 Dialog |
| `/readConfig` | 按字节流导入排版配置 |
| `/addToBookshelf` | 加书架 |
| `/importonline`（host = `booksource`/`rsssource`/`replace`） | 同上 |
| **其它** | `determineType()` 探测 |

### 3.3 兜底探测：`determineType` + `importJson`

没写 path 时走 `OnLineImportViewModel.determineType()`（L73–L104）：

1. 发一次请求，看 `Content-Type`
2. `application/zip` / `application/octet-stream` → 当排版配置，走 `importReadConfig`
3. 否则把 body 落到外部缓存 `scheme_import_cache.json`，再调 `importJson(file.toUri())`

> 💡 **为什么要落盘再读**：保证只下载一次。`importJson` 只接受 `Uri`，
> 落盘后才能复用文件读取路径，避免「探测一次 + 导入一次」两次请求。

`BaseAssociationViewModel.importJson()`（L15–L50）先试 JSONPath `$[0]`（数组首元素），
再试 `$`，然后**按顶层字段名嗅探类型**：

| 字段 | 判定为 |
| --- | --- |
| `bookSourceUrl` | bookSource |
| `sourceUrl` | rssSource |
| `pattern` | replaceRule |
| `themeName` | theme |
| `showRule` | dictRule |
| `name` + `rule` | txtRule |
| `name` + `url` | httpTts |
| 都不匹配 | 报错「格式不对」 |

> 💡 **这套「字段名即类型标签」的约定值得借鉴**：不需要额外的 `type` 字段，
> 拿到任意 JSON 都能猜出是什么。桃花源以后要加多种导入格式时可以照抄这个思路。

### 3.5 核心：`importSources(text)`

**整条链路只有一个核心函数**：`BookSourceViewModel.importSources()`（L455）。
所有入口（深链 / 本地文件 / 二维码 / 网络导入弹窗 / 剪贴板）最后都汇到它。

**第一步：判定输入是什么**

```kotlin
val text = if (input.isAbsUrl()) {
    okHttpClient.newCallResponseBody {
        if (input.endsWith("#requestWithoutUA")) {
            url(input.substringBeforeLast("#requestWithoutUA"))
            header(AppConst.UA_NAME, "null")
        } else url(input)
    }.decompressed().text("utf-8")
} else if (input.isUri()) {
    input.toUri().inputStream(application).getOrThrow().bufferedReader().use { it.readText() }
} else input
```

`StringExtensions.kt:32` 的两个判定都是**前缀匹配**：

```kotlin
fun String?.isUri() = this != null && (startsWith("file://", true) || isContentScheme())
fun String?.isAbsUrl() = startsWith("http://", true) || startsWith("https://", true)
```

> 💡 **`#requestWithoutUA` 后缀**是个精巧的小设计：URL 以它结尾时剥掉后缀、
> 并把 User-Agent 置为 `"null"`。给那些「见到 UA 就返回拦截页」的源站留后门。
> 桃花源的 `BookSourceDirectory` 也在跟 Cloudflare 一类站点打交道，这个技巧可复用。

**第二步：解析 JSON**

`parseImportSources()`（L505）：

| 文本形态 | 处理 |
| --- | --- |
| `[...]` | `GSON.fromJsonArray<BookSource>` — 标准书源合集 |
| `{...}` 含 `sourceUrls` 数组 | **订阅式索引**：逐个 URL 下载 → 递归解析 → `flatMap` 合并 |
| `{...}` 其它 | `GSON.fromJsonObject<BookSource>` — 单个书源 |
| 其它 | 抛 `invalid_format` |

⚠️ **细节**：
- `sourceUrls` 的递归调用**没有深度上限、没有环检测**（`flatMap` 里直接递归）
- 最后有一道硬校验：`require(sources.all { it.bookSourceUrl.isNotBlank() })`
  —— **任一源缺 `bookSourceUrl`，整批失败**，不是跳过那一条

**第三步：算 diff，不直接入库**

```kotlin
val old = repository.getBookSource(source.bookSourceUrl)
val status = when {
    old == null                                -> ImportStatus.New
    source.lastUpdateTime > old.lastUpdateTime -> ImportStatus.Update
    else                                       -> ImportStatus.Existing
}
isSelected = status != ImportStatus.Existing   // 已存在的默认不勾
```

> ⚠️ **判定去重/更新的唯一依据是 `lastUpdateTime`**。
> 也就是说**书源作者必须维护这个字段**，否则下游永远判为「已存在」。
> 这是生态约定，不是代码可改的东西。

**第四步：用户确认后才落库**

`saveImportedSources()`（L566）应用三条保留策略：

| 策略 | 效果 |
| --- | --- |
| `keepOriginalName` | 保留本地旧名字 |
| `keepOriginalGroup` | 保留本地旧分组 |
| `keepOriginalEnable` | 保留本地启用/发现开关 |
| `customOrder` | **总是**沿用旧值（更新后位置不变） |
| `customGroup` / `isAddGroup` | 统一改分组，或追加分组 |

默认值来自全局设置 `importKeepName` / `importKeepGroup` / `importKeepEnable`。

**第五步：真正写库**

```kotlin
SourceHelp.insertBookSource(*sources.toTypedArray())
ContentProcessor.upReplaceRules()
```

`SourceHelp.insertBookSource()`（L128）还有两道：

1. **18+ 拦截**：`assets/18PlusList.txt`（base64 编码的域名表）比对
   `bookSourceUrl` 的主域（取 host 最后两段），命中就 toast 并**跳过**
   —— 这是导入阶段**唯一**的内容过滤
2. **排序校正**：异步 `adjustSortNumber()`，当 `maxOrder > 99999` /
   `minOrder < -99999` / 存在重复序时整体重排 `customOrder`

`BookSourceDao` 是 `@Insert(onConflict = OnConflictStrategy.REPLACE)`，
主键 `bookSourceUrl` → **同 URL 直接覆盖**，天然实现「更新」。

### 3.6 其它入口（旁路）

| 入口 | 路径 | 特点 |
| --- | --- | --- |
| 文件关联 | `FileAssociationActivity`（manifest 里注册 `.json` 等） | 走 `importJson` 嗅探 |
| Web API | `BookSourceController` 的 `POST /saveSource`、`/saveSources` | **直插 DAO**，跳过预览，**也没有 18+ 过滤** |

### 3.7 数据格式要点（独立实现时需要对齐）

`BookSource` 实体**没有任何 `@SerializedName`** —— JSON 键名就是 Kotlin 属性名。
表名 `book_sources`，主键 `bookSourceUrl`。

`BookSourceType` 四个取值：

```
0 = 文本   1 = 音频   2 = 图片   3 = 只提供下载服务的网站
```

> ⚠️ 这两个是实现互操作时**必须精确对齐**的地方：
> 键名写错一个字母，用户的源就导不进来；类型码认错，UI 会显示错。

## 四、能不能加进桃花源（结论）

### 4.1 导入部分：可做，且不痛

上半段（§3.1–§3.5）**没有一行依赖 Android**，纯 JSON 处理。
桃花源已有 `dart:convert`、`http`、`shared_preferences`，**零新依赖**。

工作量估计：**半天到一天**。

### 4.2 能用部分：这才是工作量

规则引擎的体量（legado 源码实测字节数）：

| 文件 | 大小 | 作用 | 可移植性 |
| --- | --- | --- | --- |
| `AnalyzeUrl.kt` | 36.4 KB | URL 模板、`{{}}` 变量替换、分页、POST body | 中 |
| `AnalyzeRule.kt` | 35.2 KB | 规则总调度、`@css:`/`@xpath:`/`@json:`/`@js:` 前缀分派 | 中 |
| `AnalyzeByJSoup.kt` | 17.9 KB | HTML/CSS 选择器 | **高**（`html` 包可替） |
| `RuleAnalyzer.kt` | 14.5 KB | 规则语法（`&&`/`||`/`@`/`##` 替换） | 中 |
| `AnalyzeByJSonPath.kt` | 6.0 KB | JSONPath | 中（要自己写或找包） |
| `AnalyzeByXPath.kt` | 4.9 KB | XPath | **高**（`xml` 包可替） |
| `AnalyzeByRegex.kt` | 1.9 KB | 正则 | 高 |
| 五个 Rule 实体 | ~4.8 KB | 规则字段定义 | 高 |
| **合计** | **≈122 KB Kotlin** | | |

**最大坎点**：大量实际书源用了 `@js:` 规则（逆序、字符串处理、解密）。
legado 内嵌 Rhino 执行 JS。Dart 侧要么引 `flutter_js`（塞 QuickJS/V8，APK +5~10 MB），
要么**不支持** —— 但会有一批源导进来却跑不动。

**更前置的问题**：桃花源目前**没有「在线书」这条链路**。实测确认：

- `lib/pages/home_page.dart` 是**本地文档库**（PDF/EPUB/TXT）
- `lib/pages/browser_page.dart` 有「朗读本页」，但是一锤子买卖
  （`evaluateJavascript(WebSpeakScript.extract)` 抽一段给 TTS），不保存、不分章、无目录
- `lib/models/structured_document.dart` 的章节结构是给本地文件设计的

要用 legado 书源，得从零补出：

```
搜索页（关键词 → 各源 searchUrl）
  ↓
结果列表（书名/作者/封面/最新章节）
  ↓
书籍详情（简介、目录入口）
  ↓
章节目录（可能几千章，要分页/懒加载）
  ↓
正文获取（每章一次请求 + 规则解析）
  ↓
转 StructuredDocument → 喂 TtsManager
  ↓
书架（进度、更新、缓存）
```

**这条链路才是 90% 的工作量。导入按钮只是插座。**

## 五、三个方案（供决策）

### 方案 A：只做「导入 + 展示」—— 半天

导入 legado JSON、列表显示名称/分组/类型/启用状态，**但不能抓书**。

不推荐单独做：用户导进来点不开，体验是负的。

### 方案 B：受限兼容 —— 1~2 周（**推荐**）

支持 `@css:` / `@xpath:` / `@json:` 和正则替换，**不支持 `@js:`**
（遇到就标记「此源不支持」并跳过）。预计覆盖 60~70% 的源。

需要新建：

```
lib/models/book_source.dart          规则模型（键名对齐 legado）
lib/services/source_importer.dart    导入解析（= 方案 A）
lib/services/rule_engine.dart        规则求值（css/xpath/json/regex）
lib/services/source_client.dart      URL 模板 + 请求 + 编码处理
lib/pages/source_search_page.dart    搜索
lib/pages/source_book_page.dart      详情 + 目录
lib/services/source_reader.dart      正文 → StructuredDocument 适配
```

可复用：`http`、`html`、`xml`、`flutter_inappwebview`（对付 Cloudflare）、
`StructuredDocument`、`TtsManager`。

### 方案 C：完整兼容 —— 不建议

要内嵌 JS 引擎、复刻 Rhino 的 API 子集、处理 legado 全部历史兼容分支。
legado 本体是 **2000+ 个 Kotlin 文件**、6.5k star、多年迭代的产物。
这不是「加个功能」，是「再写一个 legado」。

## 七、建议路线（我倾向的顺序）

### 7.1 推荐：倒过来做

如果目标是「让桃花源能听网络小说」：

1. **先做「书架 + 在线章节 + 朗读」最小骨架**，
   用**一个写死的源**（针对某一个站，硬编码 CSS 选择器）跑通整条链路
2. 跑通后会发现规则引擎要什么、不要什么 —— 这时再抽象成可配置模型
3. 最后才是「导入 legado 格式」这层薄壳

> ⚠️ **反过来（先做导入）的后果**：得到一个装满规则但无处执行的空壳，
> 然后为了让它有意义，被迫一次性把整个引擎 + UI 链路都建起来 ——
> 这是最容易半途而废的路径。

### 7.2 想先见效：更轻的路子

已有 `flutter_inappwebview` + 「朗读本页」，可以加：

> **「把当前页按章节朗读」** —— 用 CSS 选择器把正文块切出来、
> 保存成本地 TXT 进文档库、交给现有 `TxtChapters` 分章。

不碰 legado 格式，**一两百行，当天能跑**。
